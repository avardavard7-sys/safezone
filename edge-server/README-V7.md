# SafeZone Bridge v7.12 — «Привязка по коду»

## Что изменилось

Раньше монтажник получал архив, в котором уже лежал `SUPABASE_SERVICE_KEY` и
`MALL_ID` объекта. Это два неприятных следствия: сервисный ключ обходит RLS
целиком (кто получил файл — получил всю базу всех объектов), и на каждого
клиента приходилось собирать свой архив вручную.

Теперь архив **один на всех**. Бридж знает только публичный anon-ключ, а к
объекту привязывается кодом из панели.

```
панель → «Добавить бридж» → код из 8 символов (живёт 24 часа)
бридж  → bridge_pair(код) → токен + собственная учётная запись
```

В ответ на привязку объект отдаёт всё, что раньше правили руками в `.env`:
идентификатор объекта, токен телеграм-бота, 23 настройки функций и правила зон
из редактора. Дальше каждый цикл бридж отмечается через `bridge_heartbeat` —
панель показывает «на связи», а бридж подхватывает свежие зоны и настройки без
перезапуска.

## Что это даёт

| | было (v7.9) | стало (v7.12) |
|---|---|---|
| Ключ в архиве у клиента | `service_key` — полный доступ ко всей базе | публичный anon-ключ |
| Права бриджа | безграничные | своя учётка, роль `security`, только свой объект |
| Объект | вписывался руками | приходит при привязке |
| Телеграм-бот | вписывался руками | из настроек объекта |
| Зоны | файл `zones.json` на диске | редактор зон в панели |
| Сборка архива | своя под каждого клиента | одна на всех |

Если бридж скомпрометирован, ущерб ограничен одним объектом, и учётка
отзывается удалением бриджа в панели.

## Установка у клиента

1. Панель → **Бридж** → «Добавить бридж» → скопировать код
2. В `bridge/.env` вписать `PAIRING_CODE=XXXXXXXX`
3. `docker compose up -d --build`
4. В логах: `Привязан к объекту «...»`, в панели бридж становится «на связи»

Токен и учётка ложатся в `bridge/data/state.json`. Папка примонтирована томом —
переживает `--build`. **Файл не удалять:** пароль сервис-аккаунта выдаётся
только при первой привязке, восстановить его нельзя. Если файл всё же потерян —
удалить бридж в панели и создать новый код, старая учётка снимется сама.

## Совместимость

Уже стоящие у клиентов установки не трогаются. Если в `.env` заданы
`SUPABASE_SERVICE_KEY` и `MALL_ID`, бридж пишет в логе «Режим совместимости» и
работает ровно как v7.9 — привязка не требуется.

## Проверено

**На живой базе (`cejwgfwmyzofnezqwbgu`)** — полный цикл прогнан целиком:
создание бриджа → `bridge_pair` → выдача токена (64 символа) и учётки
(пароль 48 символов) → `bridge_heartbeat` → статус `online`, код погашен в
`null`, зоны и настройки пришли в ответе. Тестовый бридж удалён, учётная
запись снята триггером, база вернулась в исходное состояние.

**Модульные тесты — 22/22** (`node test-pairing.mjs`, без ONNX и без сети):
атомарная запись состояния, битый JSON, нормализация кода, просроченный код,
сетевая ошибка RPC, повторное использование кода без пароля, отсутствие
мусорного состояния после неудачи, повторный старт без запроса пароля, переезд
объекта, неверный пароль учётки.

**Не проверено здесь:** работа с настоящими камерами и ONNX-инференс —
`onnxruntime-node` тянет пакет с закрытого в песочнице ресурса. Прогнать на
месте: `node test-local.mjs` (169 тестов) и `docker compose logs -f bridge`.

# SafeZone Bridge v7.6 — «ONVIF и кнопка в админке»

## v7.6: камеры находятся сами

**Было:** монтажник ищет IP через сканер, гадает путь (`/cam/realmonitor` или
`/Streaming/Channels/101`), вбивает всё руками, ошибается в пароле.

**Стало:** кнопка «Найти камеры» → список с моделями, разрешениями и готовыми
RTSP-адресами → «Проверить» показывает живой кадр → «Добавить».

### Как работает (onvif.js, без внешних зависимостей)

Два способа поиска, второй — потому что первый работает не везде:

1. **WS-Discovery** — UDP multicast на 239.255.255.250:3702. Быстро, находит
   всё разом. Но мультикаст часто зарезан в Docker Desktop на Windows/Mac.
2. **Развёртка подсети** — на каждый IP шлём `GetSystemDateAndTime`
   (единственный ONVIF-вызов без авторизации). Медленнее, работает всегда.
   Включается автоматически, если мультикаст ничего не дал.

Дальше камера **сама сообщает** свой RTSP: `GetProfiles` → `GetStreamUri` для
каждого профиля (основной поток и субпоток отдельно), плюс `GetSnapshotUri`
для HTTP-снапшотов. Авторизация — WS-Security UsernameToken с дайджестом
`Base64(SHA1(nonce + created + password))`.

### API бриджа (api.js)

Бридж поднимает локальный HTTP на `127.0.0.1:8099` — наружу порт не торчит:

| Эндпоинт | Что делает |
|---|---|
| `GET /health` | жив ли бридж, версия, какие провайдеры настроены |
| `POST /discover` | ONVIF-поиск, отдаёт готовые к добавлению камеры |
| `POST /probe` | снять кадр с камеры + прогнать детектор, вернуть превью |

Панель на Vercel, а браузер оператора — на том же ПК, где бридж. Поэтому
`localhost` доступен. CORS настроен.

### Компонент для админки

`admin-CameraDiscovery.tsx` — готовый React-компонент со всеми кнопками.
Положить в `components/`, подключить на странице камер:

```tsx
import CameraDiscovery from '@/components/CameraDiscovery';
<CameraDiscovery onAdd={(cam) => { /* твоё сохранение в Supabase */ }} />
```

⚠️ **Mixed content:** если админка открыта по `https`, браузер заблокирует
запрос к `http://127.0.0.1`. Варианты: открывать панель локально по http,
либо `API_HOST=0.0.0.0` и ходить по IP машины.

### Что протестировано, а что нет

**Протестировано (112/112):** разбор реальных ответов Dahua/Imou и Hikvision,
дайджест WS-Security по формуле стандарта, извлечение обоих потоков, весь цикл
против мок-камеры, HTTP-API включая CORS-preflight и ошибки авторизации.

**НЕ протестировано вживую:** поиск настоящей камеры в сети — в песочнице нет
ни камер, ни мультикаста. Проверять на Imou (у неё ONVIF в характеристиках).
Если мультикаст не сработает в Docker Desktop — впиши подсеть `192.168.10`
в поле, включится развёртка.

# SafeZone Bridge v7.9 — «Команды из облака»

## Проблема, которую это решает

Кнопки «Найти камеры» и «Проверить» в v7.7 ходили напрямую на
`http://127.0.0.1:8099`. Но панель у клиента открыта по **https**, а браузер
запрещает защищённой странице стучаться на незащищённый localhost
(mixed content) — это встроенная защита, кодом не обойти.

Обходной путь «пусть клиент поднимет панель локально» нерабочий: у клиента
нет исходников и не будет.

## Решение: очередь команд через Supabase

```
панель  ──insert──▶  bridge_commands (pending)
бридж   ──poll────▶  забирает, выполняет, пишет result
панель  ──select──▶  показывает результат
```

Бридж и так опрашивает Supabase каждые 5 секунд — плумбинг уже был.
Прямое соединение браузер→бридж больше не нужно **вообще**.

Работает: из облачной панели по https, **с телефона**, из другой страны.
Настройка сети не требуется. Клиенту не нужно ничего устанавливать.

**Безопасность:** в команде `probe` приходит пароль камеры. Сразу после
выполнения бридж затирает `params` — пароль не залёживается в базе.
Проверено тестами, в том числе для случая ошибки.

Таблица закрыта RLS по объекту: чужие команды не видны и не создаются.
Команды старше суток удаляются функцией `cleanup_bridge_commands()`.

Тесты: **169/169**, из них 11 на очередь (выполнение, затирание паролей,
ошибки, отсутствие таблицы, защита от двойного запуска).

# SafeZone Bridge v7.5 — «Зоны сервиса»

## v7.5: правила на таймерах — полностью бесплатно, без облака

Два сценария кофейни работают **на локальном детекторе + геометрии + таймерах**.
Облако не вызывается ни разу: цена сценариев — **$0 навсегда**, независимо от
числа камер и срабатываний.

**1. Гость у стойки, бармена нет 5 минут** (`no_staff`)
Две зоны: гостей и персонала. Гость есть, за стойкой пусто → отсчёт.
Ровно на 300-й секунде — тревога, дальше повтор каждые 5 минут, пока не
появится сотрудник. Бармен вернулся → таймер обнуляется.
Кто бармен, а кто гость, определяется **зоной, а не внешностью** — никакого
распознавания лиц и формы.

**2. Гости ушли, посуда не убрана 5 минут** (`uncleaned`)
Зона стола: посуда есть, людей нет → через 5 минут «нужна уборка».
Гости за столом или посуду унесли → тишина.
Классы посуды берутся из COCO: `cup, bowl, wine glass, bottle` (настраивается
через `DISH_CLASSES`). **Тарелок в COCO нет** — для кофейни хватает чашек,
для ресторана с тарелками нужен свой дообученный детектор (Фаза 2).

Ещё правила из коробки: `empty_zone` (пост без сотрудника), `occupied`
(люди в зоне дольше N — очередь, топтание).

**Анти-дребезг.** Детектор моргает: чашка пропала на кадр — и наивный таймер
обнулился бы, не досчитав до 5 минут никогда. Условие считается нарушенным
только если ложно дольше `ZONE_GRACE_SEC` (15 с). Проверено тестом: ложное
появление бармена на один кадр не сбивает отсчёт.

**Точность времени** — ±один цикл опроса (5 с): тревога приходит на 300–305-й
секунде.

### Как настроить зоны

1. Возьми кадр с камеры (скриншот из VLC или из тревоги в Telegram)
2. Открой **`zone-editor.html`** в браузере (работает офлайн), перетащи кадр
3. Кликай по углам зоны — **по полу, а не по головам**: система смотрит, где
   человек стоит
4. «Собрать zones.json» → скопировать → вставить в `bridge/zones.json`
5. `docker compose restart bridge` — пересборка не нужна, файл смонтирован томом

⚠️ **Зоны не должны накладываться.** Иначе гость за столом посчитается ещё и
гостем у стойки, и правила сработают крест-накрест (для этого есть отдельный
тест в наборе).

Тесты: 84/84 (`node test-local.mjs`), включая точность 5 минут, повторы,
сброс при возврате сотрудника, анти-дребезг и оба сценария целиком.

# SafeZone Bridge v7.4 — «Дальнозоркость»

## v7.4: люди на дальнем плане + свежие ключи Gemini

**Проблема.** Кадр 2304×1296 ужимается в 640×640 для детектора — человек
дальше ~15 метров превращается в пятно 20-60 пикселей и не детектится.

**Решение (tiles.js).** Тайловый проход: кадр режется на перекрывающиеся
куски, каждый детектится в полном разрешении, находки склеиваются общим NMS
(дубли из зон перекрытия схлопываются по центрам — важно для мелких боксов).

**Замеры на 2304px-кадре (yolox_s):**

| Рост человека | Полный кадр | Тайлы 2×2 | Тайлы 3×3 |
|---|---|---|---|
| ~84px | частично | ✓ | ✓ |
| ~62px | слеп | ✓ | ✓ |
| ~48px | слеп | ✓ | ✓ |
| ~37px | слеп | слеп | ✓ |

Предел детекции по дальности вырос в ~2-3 раза.

**Умное расписание (TILED_DETECT=auto):** тайлы гоняются раз в
TILED_EVERY_N (5) циклов на пустой сцене; как только дальний человек найден —
«прицел» держится каждый цикл, пока он не уйдёт или не приблизится. CPU-цена
2×2 = 4 доп. вызова детектора (~1.2 с), только когда есть смысл.

**Честные ограничения:** на дистанции ловим ПРИСУТСТВИЕ (вторжение,
появление) — распознавание действий (драка/падение/курение) на 50px людях
ненадёжно физически. Плотная группа дальних может посчитаться как один
(дедуп мелких боксов). Ночь/ИК на дальнем плане не тестировались.
Для очень дальних планов (шахта, парковка): TILED_GRID=3.

## v7.2: локальная VLM и режим LOCAL_ONLY (Фаза 3)

Вместо облака кадр может анализировать **локальная визуальная модель**
(Qwen3-VL-2B, Apache-2.0) через ollama / llama.cpp / LM Studio — бридж говорит
по OpenAI-совместимому протоколу, подходит любой из них.

**Зачем это продавать:**
- 🔒 **LOCAL_ONLY=true** — ни один кадр не уходит в интернет. Для воинских
  частей, школ, гособъектов это не фича, а условие контракта.
- 💰 $0 за анализ — вообще без облачных ключей.
- 🌐 Работает при отрубленном интернете (тревоги в Telegram не уйдут, но
  события в локальный лог пишутся, Supabase догонит при появлении сети).

**Включение (вариант А — ollama уже стоит на ПК):**
```
ollama pull qwen3-vl:2b
# в bridge/.env:
LOCAL_VLM_URL=http://127.0.0.1:11434/v1
LOCAL_ONLY=true        # или false — тогда локальная первая, облако как запас
docker compose up -d --build
```

**Вариант Б — всё в докере:**
```
docker compose --profile localvlm up -d --build
docker exec safezone-vlm ollama pull qwen3-vl:2b
# .env: LOCAL_VLM_URL=http://127.0.0.1:11434/v1
```

**Честно про скорость и качество:**
- 2B-модель на CPU: ~5–30 сек/кадр в зависимости от машины. Поэтому в
  LOCAL_ONLY доп. RAPID-взгляды отключены (динамику уже проверил burst-анализ
  скелетов), а верификация драк/краж оставлена — точность важнее.
- 2B слабее облачной Gemma 27B: жди больше пропусков тонких вещей (зажигалка
  в кулаке, вейп). Компенсация — локальные скелеты/трекер ловят сам ЖЕСТ и
  передают VLM подсказку. Для параноидальных объектов бери `qwen3-vl:8b`
  (нужно ~10ГБ RAM) — качество заметно выше.
- Если тега `qwen3-vl:2b` в ollama вдруг нет — `ollama search qwen3-vl`
  и возьми ближайший (4b тоже ок).
- Поведение при упавшей VLM в LOCAL_ONLY: анализ останавливается, облако НЕ
  вызывается (политика), в Telegram уходит предупреждение раз в 10 минут.

**Что тестировалось:** протокол/парсинг/таймауты — против мок-сервера
(10 тестов), плюс статические гарантии, что при LOCAL_ONLY код физически не
доходит до облачных ярусов. **Что проверить на месте:** качество ответов
конкретной модели на твоих камерах — прогони день в LOCAL_ONLY=false и сравни
вердикты local-vlm с облаком в логах.

## v7.1: сменные позы — вторая AGPL-мина обезврежена

`yolov8n-pose` (AGPL) теперь можно заменить на **RTMO-m** (mmpose, **Apache-2.0**) —
one-stage мультиперсонная поза, вся сцена за один проход:

| POSE_MODEL    | Лицензия | Латентность* | Тест-фото (4 чел, один перекрыт) |
|---------------|----------|--------------|-----------------------------------|
| yolov8n-pose  | AGPL ⚠️  | 120–185 мс   | 3/4 — перекрытого не видит        |
| rtmo_m        | Apache   | 500–610 мс   | **4/4**, conf 97/97/90/71         |

*CPU тестовой среды. Декод RTMO сверен численно с v8n-pose: на общих людях
суставы расходятся в среднем на 0.8–2.7% кадра — модели согласны друг с другом.

Переключение: `POSE_MODEL=rtmo_m` в .env. Дефолт — `yolov8n-pose` (быстрее;
на слабых клиентских ПК burst 8 кадров с RTMO займёт ~4–5 сек — прогони
`node bench-models.mjs` на месте и реши). Если ставишь rtmo_m на слабый ПК —
снизь `BURST_FRAMES=5`.

Полностью Apache-чистый профиль для B2G/госзаказчика:
```
DETECTOR=yolox_s
POSE_MODEL=rtmo_m
```

## Что нового в v7.0

### 1. Letterbox вместо растягивания (баг-фикс геометрии)
Раньше кадр 16:9 сплющивался в квадрат 640×640 — люди «толстели», лежачие
пропорции ломались, «падение» ложно срабатывало на широкоугольных камерах.
Теперь кадр вписывается с сохранением пропорций, все координаты честные.
**Затронуты все камеры, ничего настраивать не нужно.**

### 2. Трекер (tracker.js) — бесплатно, локально
Каждый человек и каждая сумка получают стабильный ID между кадрами
(логика ByteTrack: двухэтапный матчинг). Что это даёт:
- **лойтеринг**: человек топчется на месте N минут (ночью → тревога);
- **брошенная вещь**: сумка лежит без людей рядом 45+ сек → облако смотрит;
- **бег** в нерабочее время → rapid-режим;
- скорость каждого человека считается локально, за $0.

### 3. Burst-серии (burst.js) — главное
При rapid-триггере (нож/огонь/падение/драка/ночь) мост снимает **8 кадров за
2 секунды одним RTSP-подключением** и прогоняет скелеты по всей серии:
- скорость запястий в **единицах роста/сек** (удар = 1.2–2.0, ходьба = 0.3–0.6);
- падение = проседание головы ≥35% роста за ≤1.2 сек + в конце лежит;
- курение = рука у рта ≥3 кадров подряд;
- драка = двое вплотную ≥2 кадров + резкое движение рук.
В облако летит **лучший кадр серии** (момент удара, а не «после») с подробной
подсказкой. Остальные кадры серии используются для верификации — **без новых
подключений к NVR**.

### 4. Сценарии проверяются ДО облака (экономия)
Раньше: камера «только пожар» → человек в кадре → облачный вызов → ответ
отброшен фильтром сценариев. Деньги потрачены.
Теперь: гейт знает `enabled_scenarios` камеры и не вызывает облако вообще,
если триггер не относится к включённым сценариям. В логах видно:
`💤 ... облако не нужно (сценарий выключен у камеры), $0`.

### 5. RAPID стал дешевле
Было: тревога → 4 облачных вызова всегда (1 + 3 доп. кадра).
Стало: 1 вызов по лучшему кадру серии; доп. взгляды (до 2) — **только если
первый вызов нашёл угрозу**, и из уже снятой серии. Ложная тревога = 1 вызов.

### 6. Сменный детектор (юридическая мина обезврежена наполовину)
`yolov8n` — лицензия **AGPL-3.0** (Ultralytics): для закрытого коммерческого
продукта это риск. Добавлен **YOLOX** (Megvii, **Apache-2.0**) — переключается
одной переменной:

| DETECTOR    | Лицензия | Латентность* | Точность на тест-фото |
|-------------|----------|--------------|------------------------|
| yolov8n     | AGPL ⚠️  | 115 мс       | 4/4 человека (слабый — 42%) |
| yolox_nano  | Apache   | 38 мс        | 3/4 (пропустил перекрытого) |
| yolox_s     | Apache   | 263 мс       | **4/4 (перекрытый — 63%)** |

*CPU в тестовой среде; на клиентских ПК цифры свои — прогони `node bench-models.mjs`.

**Рекомендация: `DETECTOR=yolox_s`** — точнее и чистая лицензия. Дефолт пока
`yolov8n`, чтобы обновление не меняло поведение без твоего решения.
(Позы `yolov8n-pose` пока остаются AGPL — замена на RTMPose = Фаза 1,
см. «Что дальше».)
